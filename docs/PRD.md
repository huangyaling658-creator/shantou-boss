## 1. 背景与问题

### 1.1 一个被忽略的事实

BOSS 直聘对求职者的每日主动沟通次数有上限，成熟账号约 100 次，新账号更低。**开会员也买不到更多**，会员宣传的「不限沟通人数」实际仍是每天 100 人，且不论对方是否已读或回复，发出去就算一次。

这意味着求职者每天手里只有一把**固定的、不可扩容的沟通额度**。

### 1.2 现有工具的解法

市面上的自动投递工具（以「即投」为代表）解决的是「怎么把额度快速花完」：设好筛选条件，工具自动搜集岗位、批量生成招呼语、逐个投出去。价值主张是「解放双手」。

这个解法在额度充裕时成立。但当额度是固定的、而市场回复率持续走低时，**把额度花得更快并不能带来更多机会**，只能更快地把机会用完。

### 1.3 我们要解决的问题

**同一把固定额度，怎么花在对的岗位上。**

具体到本产品的第一使用者：目标是进大厂（字节、腾讯、快手、小红书等）做 AI 产品相关岗位。核心诉求不是「投得多」，而是：

1. 在大厂范围内，**不漏掉**任何一个可能匹配的岗位
2. 在召回的岗位里，**准确判断**哪些真的匹配我的简历
3. 招呼语要**像真人写的**，而不是模板套出来的
4. **投过的不要再投**

## 2. 目标用户

**v1.0 的唯一用户是产品作者本人。** 不做账号体系、不做付费、不做多用户。

这是刻意的取舍：先把「自己每天真的在用」跑通，再谈是否对外。一个自己都不用的求职工具，做给别人也没有说服力。

**潜在扩展用户画像**（v2.0 之后再考虑）：目标明确的求职者，只想投特定几家公司，不接受海投，对招呼语质量有要求。

## 3. 竞品：即投

### 3.1 它是什么

Chrome / Edge 扩展，定位「海投工具，解放双手」。三大功能：自动批量投递、AI 定制招呼语、简历截图发送。免费额度 + 7日/30日会员制，另有最高 45% 佣金的推广分销。

### 3.2 它的能力边界（源码核实）

**做得好的：**
- 十二个筛选维度，覆盖城市、岗位、行业、区域、工作性质、HR 活跃度、福利、薪资、经验、学历、公司规模、融资阶段
- HR 活跃度筛选（只投在线 / 3日内活跃 / 本周内活跃），零成本但对回复率影响极大
- 选到会大幅缩小池子的条件时，当场给黄色警示说明代价
- 三级招呼语自定义（全局 / 岗位组 / 单岗位）+ 出厂兜底语，容错链完整
- 风控自适应退避：12 小时滚动窗口统计验证码触发次数，自动降速或停投
- 复放页面自身的真实请求来翻页，不自己拼 URL

**它没有的：**
- **没有任何公司维度的筛选**。能筛行业、规模、融资阶段，但无法指定「只要字节、小红书、快手」
- **没有匹配度评估**。召回即候选，唯一的排序是平台默认排序
- **没有效果数据**。投出去之后发生了什么，工具不知道，用户也不知道
- 招呼语质量依赖通用大模型 + 通用 prompt，无个人语感约束

### 3.3 结论

即投把「执行效率」做到了很高的水准，但**它的产品目标里没有「投得准」这件事**。这不是它做得不好，是它的定位就是海投。

## 4. 产品定位与差异化

### 4.1 定位

> **闪投：只投你想去的公司，只投真的匹配的岗位。**

### 4.2 三个差异点

| # | 差异点 | 即投 | 闪投 |
|---|---|---|---|
| 1 | **公司白名单** | 无 | 内置 500 家公司库（大厂 / AI 模型公司 / 音乐泛娱乐等分组），可勾选、可搜索添加、可自定义分组 |
| 2 | **匹配度评估** | 无 | LLM 四维打分（职责 / 能力 / 行业 / 级别），每维必须给出「JD 原句 + 简历原句」的证据配对，并强制输出短板 |
| 3 | **招呼语语感** | 通用 prompt | 注入作者自己的 AI 通病病例库（「省」与「演」两大家族）作为硬性禁令，强制引用 JD 原词和简历中的具体项目名与数字 |

其中第 3 条是**竞品无法复制**的：它依赖一份长期积累的个人写作病例库，不是换个模型就能补上的。

### 4.3 不打的仗

- 不比谁投得多
- 不比谁速度快
- 不做推广分销
- 不做付费会员

## 5. 核心概念

下表左列是**内部术语，只出现在代码和技术文档里**。界面上一律用右列的说法。

| 内部概念 | 定义 | 界面说法 |
|---|---|---|
| **一次任务** | 从配置到投递完成的一轮完整流程，对应一个 taskId | 一轮 |
| **召回** | 从 BOSS 抓取符合结构化条件的岗位列表 | 搜索岗位 |
| **廉价过滤** | 只用列表页已有字段做的过滤和排序，不拉 JD，零额外请求 | （不外露） |
| **精排** | 拉取 JD 全文后，由 LLM 做的四维打分 | （不外露） |
| **审核池** | 精排后呈现给用户勾选的岗位集合，100 到 120 条 | 搜索结果 |
| **分档** | 按匹配分数划分的区间：90+ / 80-90 / 70-80 / 60-70，地板分 60 | （不外露） |
| **每日额度** | BOSS 允许的主动沟通次数，不可查询，只能探测 | 今日可投 |
| **勾选即标注** | 用户的勾选与剔除动作，同时作为匹配模型的评估标签 | （不外露） |

## 6. 用户主流程

界面就是这条流程本身，五步顺着往下走（界面细节见第 8 节）。

```
① 上传简历
   拖入两张简历截图
   视觉模型自动 OCR 成文本（可展开修正）
   ※ 不需要填任何 API Key，密钥内置
        ↓
② 选择目标
   勾选目标公司 → 选城市 → 选期望岗位 → 展开更多筛选
   实时看预估：预计能搜到 N 个岗位，够不够今天的 75 个额度
        ↓
③ 搜索岗位（自动，约 15 到 30 分钟）
   底层依次跑：召回 → 廉价过滤 → 拉 JD → 四维打分
   界面上只说「正在搜索」并给进度
        ↓
④ 审核岗位（人工闸口）
   结果列表默认全部勾选，用户取消不想要的
   每张卡可展开看分数、四维拆解、证据配对、短板
        ↓
⑤ 生成打招呼语（自动）→ 审核（人工闸口）
   逐岗生成，每条可直接编辑、可重新生成
        ↓
⑥ 一键投递（自动，约 15 到 22 分钟）
   逐岗：详情页 → 点沟通 → 发招呼语 → 连发两张简历截图
   进度条 + 实时日志，投了谁、跳过谁、为什么跳过
   触发验证码自动暂停，处理完可断点续投
```

## 7. 功能需求

### P0 · 不做就不可用

| ID | 功能 | 描述 | 验收标准 |
|---|---|---|---|
| F-01 | 简历管理 | 只上传截图；用视觉模型 OCR 成文本供打分和招呼语使用 | 用户只做上传一个动作，文本自动产出且可修正 |
| F-02 | 密钥内置 | Key 写在 secrets.js 里作为兜底，不在界面上暴露 | 用户看不到也不需要填任何 Key |
| F-03 | 公司白名单 | 内置分组勾选 + 搜索添加 + 自定义分组保存 | 勾选公司后能正确解析出 brandId 并精确匹配到岗位 |
| F-04 | 岗位词与城市 | 多选，支持从 BOSS 字典挑选与自定义输入 | 支持「全国」范围 |
| F-05 | 结构化筛选器 | 行业 / 工作区域 / 工作性质 / HR活跃度 / 福利 / 薪资 / 经验 / 学历 / 公司规模 / 融资阶段 | 全部正确拼入 BOSS 原生请求参数，不增加请求数 |
| F-06 | 三通道召回 | 按勾选公司数自动切换 A/B/B' 通道 | 勾 100 家公司时请求量不超过勾 1 家时的 2 倍 |
| F-07 | 廉价过滤 | 硬规则淘汰 + 轻量排序 + 截断到 300 | 不拉任何 JD 即可完成 |
| F-08 | JD 抓取 | 串行，间隔 3 秒 | 不触发 `code:37` 软封锁 |
| F-09 | 四维打分 | LLM 输出总分 + 四维分 + 证据配对 + 短板 | 每个维度必须有 JD 原句与简历原句配对，缺失即判该次打分无效并重试 |

| F-11 | 岗位审核 | 结果列表默认全选，支持取消勾选、展开评分详情、编辑与重生成招呼语 | 所有用户动作落库 |
| F-12 | 去重 | L1 岗位ID / L2 指纹 / L3 JD相似 / L4 HR冷却 / L5「继续沟通」判别 | 同一岗位在任何情况下不重复投递 |
| F-13 | 分档凑满 | 高分优先，不足降档，地板分 60 | UI 如实显示分档构成，可一键关闭凑数 |
| F-14 | 投递执行 | 详情页点沟通 → 发招呼语 → 连发两张截图 | 投递前自动关闭 BOSS 自带招呼语开关，任务结束恢复 |
| F-15 | 额度闸门 | 软上限 75/批，日上限 150，硬探测真实上限 | 探测到上限立即停止并记录 |
| F-16 | 风控退避 | 验证码检测 + 12小时滚动窗口 + 自动降速/停投 | 触发验证码立即暂停并落盘进度，可断点续投 |
| F-17 | 数据落库 | 全字段写 IndexedDB | 见技术方案第 4 节字段清单 |

## 8. 界面：一条线性流程

### 8.1 原则

**界面按用户做事的顺序排，不按我们开发的模块排。**

不设「配置 / 审核 / 看板」这类标签页。标签页是技术模块的切分方式，对使用者来说意图不明：他并不想知道哪些属于配置、哪些属于审核，他只想知道「现在该干什么、下一步是什么」。

**用词也不透传内部概念。** 界面上说「搜索岗位」，不说「召回」；说「打招呼语」，不说「greeting 生成」。召回、精排、廉价过滤这些词只活在代码和技术文档里。

### 8.2 四屏

不做步骤卡片和序号。**条件设置是一条长滚动**，分区靠「粗体标题 + 细分隔线」，用户从上到下填完直接点底部按钮。搜索之后切到结果屏，往后依次是打招呼语屏和投递屏，顶部有返回。

```
屏一 · 条件设置（一条长滚动）
  图片版简历      两张截图，后台自动识别成文字
  目标公司   ★    按分组平铺，可搜索（竞品没有这一项）
  目标城市        热门城市平铺 + 展开更多 + 搜索
  期望职位        简历推荐 + 常用岗位按职类平铺 + 搜索 + 自创词条
  公司行业 / 工作性质 / HR活跃度 / 福利待遇 /
  薪资待遇 / 工作经验 / 学历要求 / 公司规模 / 融资阶段
                  全部平铺，不折叠不藏
  ［重置］［开始搜索］
        ↓
屏二 · 搜索结果    进度 → 过滤漏斗 → 列表（默认全选）
        ↓
屏三 · 打招呼语    逐条生成，可编辑可重生成
        ↓
屏四 · 投递        进度 + 实时日志
```

### 8.2.1 视觉规范

| 元素 | 规范 |
|---|---|
| 分区 | 无卡片边框，粗体标题 17px + 底部细分隔线 |
| 选项 | 大圆角胶囊，内边距 9×18，字号 14.5 |
| 单选选中 | 实心橙底白字 |
| 多选选中 | 橙色描边橙字，白底 |
| 已选项 | 浅橙底 chip，带 × |
| 搜索框 | 全圆角，左放大镜，右清除 |
| 代价警示 | 浅橙底 + 橙边框 + ⚠ |
| 底部条 | 固定，左「重置」描边，右主操作实心 |

**两个默认值是有意设的**：HR 活跃度锁「3日内活跃」，工作性质锁「全职」。前者零成本但对回复率的影响可能超过我们的四维打分，后者是因为本产品不是给找实习兼职的人用的。

### 8.3 三个交互决定

**搜索结果默认全选。** 用户的动作是「取消不想要的」，不是「挑出想要的」。取消比挑选省力，而且默认全选符合「搜出来的本来就该是匹配的」这个预期。

**能点就不让打字。** 岗位不做纯输入框，而是「简历推荐 + 常用岗位按职类平铺 + 搜索补充 + 自创词条」四层，让人下意识地点，不用想岗位名该怎么写。打字只是最后的兜底。

**内部处理不拦人。** 简历 OCR 在后台静默跑，用户传完图立刻就能往下选公司选城市，不显示阻塞式进度，也不禁用任何按钮。识别结果要到生成打招呼语那步才真正需要，那时早跑完了。

**每一步之后都有人工闸口。** 搜索完停下来让用户审岗位，生成完停下来让用户审招呼语，确认了才投。这是「闪投」的核心，不是流程负担。

**投递过程必须持续告知在干什么。** 进度条加实时日志，每一条显示投了谁、跳过了谁、为什么跳过。这一段要跑十几二十分钟，不能是个黑盒。

**搜不到结果时要说清死在哪一层。** 「没搜到，放宽条件再试」等于什么都没说。必须摊开过滤漏斗：平台搜到多少、剔除猎头多少、公司不在名单里多少、岗位名对不上多少。三种原因对应三种完全不同的处理方式。

### 8.4 不放在主流程里的

数据导出、重新开始一轮这类低频操作收进右上角的「⋯」菜单。

投递漏斗看板等 v2.0 接上回复统计后再单独出一屏，现在不占主流程的位置。

## 9. 业务规则

### 9.1 额度

```
软上限：75 / 批
日上限：150（绝对红线）
真实上限：不可查询，只能探测
探测方式：检测到「次数已达上限」提示 / 验证码 / code:37 → 立即停止并记录
```

### 9.2 分档凑满

```
先投 90+ 档
不足 75 → 放宽到 80+ 档
仍不足 → 放宽到 70+ 档
仍不足 → 放宽到 60+ 档
仍不足 → 投多少算多少，绝不低于 60 分
```

**地板分 60 是硬约束**。没有它，岗位荒的日子系统会凑一堆无关岗位，产品就退化成海投了。

UI 必须如实显示构成，并允许一键关闭凑数、只投高分。每条记录写入 `dispatch.tier`，这是将来验证匹配模型是否有效的唯一切片维度。

### 9.3 去重

五层，任一命中即跳过，详见技术方案第 7 节。

**不做冷启动回读**（已决策）。后果是插件不知道装它之前手动聊过哪些岗位，由 L5「继续沟通」按钮判别在投递那一刻兜底。代价是这类岗位仍会占用一次详情页请求，但不会真的发出招呼语，也不消耗沟通额度。

### 9.4 招呼语降级链

LLM 超时或失败绝不阻断投递：

```
岗位定制招呼语 → 岗位组通用招呼语 → 用户全局自定义 → 出厂兜底语
```

### 9.5 风控退避

```
12 小时滚动窗口内验证码触发次数：
  0 次  → 正常速度
  1 次  → 降速档（间隔翻倍）+ 弹窗告知
  ≥2 次 → 拒绝整批，冷却到窗口滑出，需手动确认才能继续
```

检测到验证码立即暂停并落盘进度，用户处理完可断点续投。

### 9.6 节奏

| 参数 | 值 |
|---|---|
| 投递间隔 | 2 到 4 秒随机 |
| 批次休息 | 每 50 个休 90 秒 |
| 并行度 | 1（串行） |
| 拉 JD 间隔 | 3 秒（硬线，1.5 秒会触发 `code:37`） |
| 禁止时段 | 0 点到 7 点 |

预计单次投递 75 个耗时 **15 到 22 分钟**。

## 11. 成功指标

如果做完一周就不用了，说明产品假设错了，后面所有功能都不值得做。

**过程指标**（记录但不考核）：

**v2.0 接上回复统计后的核心指标**：分档回复率是否单调递减。这是「闪投优于海投」的唯一证据。

## 12. 风险与合规

| 风险 | 说明 | 应对 |
|---|---|---|
| **违反平台协议** | 抓取与自动投递违反 BOSS 用户协议 | 半自动形态（用户审核后投递）风险显著低于无脑海投，但不为零。第一版自用 |
| **账号被限流** | 平台第一层惩罚是弹验证码而非封号 | 探到边界即停，不硬顶；验证码触发后自动降速或停投 |
| **匹配不准** | LLM 打分可能有偏 | 强制证据配对 + 强制输出短板 + 人工审核闸口。数据从第一天存，为将来校准留素材 |
| **数据丢失** | 浏览器数据被清 | JSON 导出 + 每日自动备份 |
| **平台改版** | BOSS 接口或 DOM 结构变更 | 复放页面真实请求而非自拼 URL；选择器集中管理，改版时单点修复 |

**若将来对外发布**：需在显著位置告知账号风险，并提供完全手动模式。

## 13. 明确不做

| 不做 | 原因 |
|---|---|
| 剔除原因选择 | 增加操作负担，收益不足以抵消 |
| 招呼语模板 A/B | 没有回复数据时无法判定胜负，做了是自欺欺人 |
| 冷启动回读历史会话 | 由 L5「继续沟通」判别零成本兜底 |
| 并行投递 worker | 75 个串行只要二十分钟，不值得引入复杂度和风控面 |
| 后端服务 | 自用场景不需要。且后端也拿不到 BOSS 登录态，改变不了架构本质 |
| 账号体系 / 付费 / 推广分销 | 不是本产品要打的仗 |
| 全自动托管模式 | 与「闪投」定位冲突，人工审核闸口是产品的核心而非负担 |
