# 闪投 · 技术方案 v0.2

> 产品名「闪投」（已定）。BOSS 直聘大厂精准投递助手。
> 文档日期：2026-09-15
> 状态：已评审通过，待开发。配套产品文档见 `PRD.md`。

---

## 0. 一句话定义

一个 Chrome 扩展。读你的简历，在你指定的大厂范围内召回岗位，用 LLM 做四维打分并给出证据，你在审核页勾选（勾选即标注），逐岗生成带你个人语感的招呼语，一键投递并连发简历截图。每天封顶 75 个，高分优先、不足降档，全程三层去重。

**与即投的根本分歧**：即投优化的是「把每日额度快速花完」，闪投优化的是「把每日额度花在对的岗位上」。同一个平台约束，两种解法。

## 1. 平台事实（已核实）

以下参数来自对即投 v1.7.1 本地安装包的源码核实（`成品/即投-boss直聘助手/`），非推测。**只取平台客观事实，不复用其代码实现。**

### 1.1 接口清单

| 用途 | 接口 | 方法 | 备注 |
|---|---|---|---|
| 岗位搜索（有关键词） | `/wapi/zpgeek/search/joblist.json` | POST | form-urlencoded，`page` 在 body |
| 岗位推荐（无关键词） | `/wapi/zpgeek/pc/recommend/job/list.json` | GET | `page` 在 URL |
| 城市字典 | `/wapi/zpgeek/common/data/city.json` | GET | |
| 期望职位字典 | `/wapi/zpgeek/common/data/expectposition.json` | GET | 岗位词选择器的数据源 |
| 商圈字典 | `/wapi/zpgeek/businessDistrict.json` | GET | 「工作区域」用 |
| 当前用户信息 | `/wapi/zpuser/wap/getUserInfo.json` | GET | 取 `zpData.encryptUserId` |
| 招呼语开关读 | `/wapi/zpchat/greeting/getGreetingList` | GET | |
| 招呼语开关写 | `/wapi/zpchat/greeting/updateGreetingV2` | POST | `status=0` 关闭 |
| 图片上传 | `/wapi/zpupload/quicklyUpload` | POST | 返回 `imgaz.bosszhipin.com` 图床地址 |
| 会话列表 | `/wapi/zprelation/friend/getGeekFriendList.json` | GET | 将来做回复统计用 |
| 岗位详情页 | `https://www.zhipin.com/job_detail/{encryptJobId}.html` | GET | |

**关键特性：这些接口同源、带 cookie 自动鉴权、无签名参数。** 在 content script 里 `fetch(..., {credentials:'same-origin'})` 可直接复放。

### 1.2 列表接口返回的可用字段

一次分页请求就能拿到，零额外成本，这是廉价过滤层的全部弹药：

```
encryptJobId      岗位唯一 ID（也是详情页 URL 的一部分）
jobName           岗位名
salaryDesc        薪资（页面上是加密字体，需解码）
brandName         公司名
jobLabels/tags    经验、学历等标签
welfareList       福利标签列表
daysPerWeekDesc   工作制（网页端绝大多数为空，不可靠）
bossOnline        HR 是否在线（boolean）
proxyJob          是否猎头代招（1 = 是）
anonymous         是否匿名岗（非 0 = 是）
securityId        后续接口调用需要的令牌
```

详情接口额外提供 `activeTimeDesc`（HR 活跃度分级文案，如「3日内活跃」）。

### 1.3 已确证的风控参数

| 事实 | 数值 | 来源 |
|---|---|---|
| 取 JD 详情的串行间隔下限 | **1.5s 会触发软封锁 `code:37`**，安全值 3s | 即投代码注释「实测」 |
| 列表翻页上限 | 即投设 20 页 | `JobCollector.maxPages` |
| 单日累计投递上限 | 即投设 150 | `DAILY_SEND_LIMIT` |
| 单批投递上限 | 即投设 75 | `SOFT_BATCH_LIMIT` |
| 风控惩罚形式 | 先弹 captcha，累积多次才硬封 | 即投风控退避注释 |
| 即投的退避策略 | 12h 滚动窗口内 captcha 1 次降速、≥2 次拒绝整批 | `CAPTCHA_*` 常量 |

**这组数字印证了你定的 75 是合理的**：它正好是竞品的单批上限，且只有日上限的一半。

### 1.4 投递链路的三个坑（已知）

1. **BOSS 自带「自动招呼语」开关必须先关**。不关的话，点「立即沟通」会先发平台默认招呼语，我们的 AI 招呼语变成第二条，HR 看到的第一句还是模板。做法：投递前调 `updateGreetingV2` 置 `status=0`，任务结束后恢复。
2. **「继续沟通」判别可用**。详情页的 `a.btn-startchat` 按钮，文案是「立即沟通」= 没聊过，「继续沟通」= 已建会话。这是去重的免费兜底，投递前读一次即可。
3. **同一 HR 的不同岗位会弹确认框**。点沟通后会跳到消息页并弹「沟通新职位」确认弹窗，需要额外点一次。

### 1.5 平台的结构性缺陷

- **双休没有结构化字段**。`daysPerWeekDesc` 网页端基本为空，只能靠岗位标题里的关键词打标（「双休/做五休二」vs「大小周/单休」）。所以「双休」这个筛选项天然不准，UI 上必须明示，像即投那样给黄色警示。
- **猎头岗和匿名岗在列表页不渲染活跃度**。`proxyJob=1` 或 `anonymous≠0` 的岗位拿不到 `activeTimeDesc`，要单独点卡片触发详情请求才能拿到。第一版建议直接把猎头岗过滤掉（我们只投大厂，猎头代招本来就不是目标）。
- **薪资字段是加密字体**，页面上显示正常但 DOM 取出来是乱码，需要解码表。

### 1.6 即投的架构（供对照）

- 后端：腾讯 CloudBase 云函数
- LLM：阿里 dashscope（通义千问），**不是 DeepSeek**
- 图床：腾讯 COS
- 投递：3 个并行 worker 跑在独立后台窗口，岗位间隔 2 到 4 秒，每批 50 个后休息 90 秒
- 埋点：`/track` 上报 device_id

**它有后端，且 LLM 走后端代付。** 我前面说「即投没后端」是错的。它需要后端是因为要做付费、额度控制、防白嫖（免费额度绑 BOSS 账号 `encryptUserId`，堵重装换 device_id）。我们第一版自用，这些都不需要。

**另一个重要发现：即投全代码库没有任何公司维度的筛选。** 它能筛行业、规模、融资阶段，但无法指定「只投字节、小红书、快手」。这确认了我们的切入点是真空白。

## 2. 系统架构

```
┌─────────────────────── Chrome 扩展（MV3）───────────────────────┐
│                                                                  │
│  Side Panel（主界面）                                             │
│   ├─ A 页 配置：简历 / 公司 / 岗位词 / 城市 / 筛选器 / 召回预估    │
│   ├─ B 页 审核：岗位卡列表（分数 + 四维 + 证据 + 招呼语）         │
│   └─ C 页 看板：今日进度 / 分档构成 / 历史（漏斗留空位）          │
│                                                                  │
│  Service Worker（编排中枢）                                       │
│   ├─ 任务状态机 / 断点续跑 / 额度闸门 / 风控退避                  │
│   ├─ LLM 调度（打分并发、招呼语流水线、超时降级）                 │
│   └─ 数据访问层（Repository 接口，本地实现）                      │
│                                                                  │
│  Content Scripts（跑在 zhipin.com）                               │
│   ├─ 请求模板嗅探（MAIN world，hook 页面自己的 joblist 请求）      │
│   ├─ 召回执行（复放分页请求 / 遍历公司页）                        │
│   ├─ JD 抓取（串行 3s 间隔）                                      │
│   ├─ 投递执行（详情页点沟通 → 聊天页发消息 + 图）                 │
│   └─ 风控哨兵（captcha 检测、code:37 检测）                        │
│                                                                  │
│  IndexedDB（全量数据）                                            │
└──────────────────────────────────────────────────────────────────┘
          │                              │
          ↓                              ↓
    通义千问 DashScope             JSON 导出备份
    （视觉 OCR + 文本打分/招呼语）  （防数据丢失）
```

### 2.1 为什么没有后端

数据量算过：每天 75 条、每条约 4KB（含 JD 全文和证据），一年约 110MB。IndexedDB 完全够。

**后端的三个触发条件，达到任意一条再上**：
1. 给别人用且由我方代付 LLM 费用（需要额度控制和防滥用）
2. 需要跨设备同步或手机端看数据
3. 需要汇总多用户数据训练匹配模型

**注意：即使上了后端也改变不了架构本质。** BOSS 的抓取和投递必须在用户登录态的浏览器里发生，服务器拿不到 cookie，做不了任何事。后端永远只能是存储 + LLM 代理。

### 2.2 迁移口子

数据访问全部走 `JobRepository` 接口，本地实现 `IndexedDBRepository` 先上，将来加 `RemoteRepository` 换实现即可，业务代码不改。LLM 调用同理，走 `LLMProvider` 接口，现在是 `QwenDirectProvider`，将来换 `GatewayProvider`。

## 3. 召回策略

### 3.1 请求量公式

```
请求数 = 城市数 × 岗位词数 × 分页数
       + (勾选公司数 ≤ 30 ? 勾选公司数 × 公司页页数 : 0)
```

**关键设计：公司维度不进笛卡尔积。** 只有城市和岗位词是乘性维度，其余十来项筛选（行业、工作性质、HR活跃度、福利、薪资、经验、学历、公司规模、融资阶段、工作区域）全是 BOSS 原生 URL 参数，拼上去不增加请求。

### 3.2 三条通道，按勾选数自动切换

| 勾选公司数 | 通道 | 做法 | 请求量特征 |
|---|---|---|---|
| 1 到 30 家 | **A · 公司页遍历** | 逐个遍历公司主页的在招职位列表 | 随公司数线性增长，但召回该公司**全量岗位**，不漏 |
| 30 家以上 | **B · 词搜 + 本地过滤** | 正常关键词搜索，抓回后在本地用公司白名单过滤 | **与公司数无关，恒定**；受分页深度限制 |
| 0 家 | **B' · 纯条件模式** | 只按岗位词搜，用公司规模/融资阶段筛质量 | 恒定 |

**补漏机制**：走 B 通道后，统计每家勾选公司实际召回数。为 0 或明显偏少的（阈值待定，暂定少于 3 个），单独对这几家追加一次 A 通道。兼顾 B 的恒定成本和 A 的完整性。

### 3.3 请求模板的获取方式

不自己拼搜索 URL。做法是在 MAIN world 注入脚本 hook `fetch`/`XHR`，**捕获页面自己发出的真实 joblist 请求**（含全部查询参数），把它当模板，只替换 `page` 字段。

理由：BOSS 的请求参数会变，自己拼容易拼错或漏参数；复放真实请求最稳。这一点即投也是这么做的，是正确解法。

拿不到模板时 fail-open，回退到 DOM 滚动采集。

### 3.4 两段过滤漏斗

```
召回（几百到几千）
   ↓  廉价过滤：只用列表页字段，零额外请求
   ↓  ① 硬规则：公司白名单 / 学历 / 经验 / 城市 / 猎头岗剔除
   ↓  ② 去重 L1+L2
   ↓  ③ 轻量打分排序（岗位名与期望词的匹配度、薪资区间、HR活跃度）
   ↓
候选（截断到 300，可配置）
   ↓  拉 JD 全文（串行，间隔 3s，这是最贵最危险的动作）
   ↓  去重 L3
   ↓  LLM 四维打分 + 证据
   ↓
审核池（100 到 120 条，按分数排序）
   ↓  用户勾选（= 标注）
   ↓  分档凑满 75
   ↓
投递队列（75）
```

**为什么必须有廉价过滤层**：拉 JD 要逐个发请求，间隔 3s，300 个就是 15 分钟。如果不先砍，几千个 JD 要拉一整天，而且请求量直接等于风控风险。列表页字段本来就在手里，用它先砍掉 90% 的噪声是白捡的。

### 3.5 岗位词扩展

A 通道不需要扩词（公司页是全量列出）。B 通道需要，由 LLM 读简历生成同义岗位名集合，例如：AI产品经理 / 大模型产品经理 / AIGC产品经理 / Agent产品经理 / 算法产品经理 / 智能助手产品经理。

用户可在 UI 上增删，也支持从 BOSS 的 `expectposition.json` 字典里挑。

### 4.2 其他表

| 表 | 用途 | 关键字段 |
|---|---|---|
| `tasks` | 一次完整任务 | taskId, 配置快照（公司/岗位词/城市/筛选器）, 各阶段耗时, 召回数, 投递数, 实际达成额度, 是否触发 captcha |

### 4.3 三个「现在不存，以后哭」的字段

1. **`score.promptVersion` + `modelId`**。没有它，将来无法判断「这批分数是哪一版模型打的」，所有历史数据作废，无法做版本对比。
2. **`annotation.decision`**。这是零成本的标注数据。用两周就能攒出几百条带标签样本，用来算 Top-N 精确率。不存的话，你只能从头人工标 100 条。
3. **`dispatch.conversationId`**。将来接回复统计时，靠它把本地记录和 BOSS 会话对上。不存的话，之前投的几百条永远算不出回复率。

### 4.4 备份

- 手动「导出全部数据为 JSON」按钮
- 每日自动导出到本地目录（可开关）
- 支持导入恢复

成本很低，但把「清浏览器数据导致全部丢失」这个最大风险按掉了。

## 5. 打分设计

### 5.1 分层

**第一层 硬门槛（规则，不用 LLM）**：学历不符、经验年限差距过大、城市不符、猎头岗、岗位大类明显不符，直接淘汰。LLM 不擅长确定性判断，而且浪费 token。

**第二层 轻量打分（规则 + 字符串匹配，不拉 JD）**：岗位名与期望词的匹配强度、薪资是否在期望区间、HR 活跃度、公司规模。用于把候选截断到 300。

**第三层 LLM 四维打分（拉 JD 后）**：

| 维度 | 权重 | 判什么 |
|---|---|---|
| 职责重合度 | 0.35 | JD 写的日常工作，我做过多少 |
| 能力技术栈 | 0.30 | 要求的技能我有几项，熟练度如何 |
| 行业与业务形态 | 0.20 | ToC/ToB、内容/工具/平台、行业是否对口 |
| 级别匹配 | 0.15 | 是高攀、平配还是低就 |

### 5.2 防止分数全挤在 85 的三个手段

1. **锚点样例**：prompt 里给一个 95 分和一个 60 分的完整例子，把标尺钉死。
2. **强制证据**：每个维度必须给出「JD 原句 + 简历原句」的配对。没有证据配对的分数不采信。这同时解决了 UI 上「为什么是 87 分」的展示需求。
3. **强制找短板**：必须输出 `concerns` 字段，至少一条。只会夸的模型给不出有区分度的分数。

### 5.3 准确度评估（不在第一版做，但数据从第一天存）

- **离线**：用 `annotation.decision` 当标签，算 Top-20 精确率和 Spearman 序相关。改 prompt 就重跑一次，有基线才知道是变好还是变坏。
- **在线**：等回复统计上线后，看 90+ / 80-90 / 70-80 三档的回复率是否单调递减。不单调 = 分数是假的。

## 6. 招呼语设计

### 6.1 形式（已定）

**一条消息发完，不分层，不等 HR 回复。** 点「立即沟通」带出招呼语，紧接着在同一会话连发两张简历截图，全部在投递瞬间完成。

### 6.2 内容规格

80 到 150 字。结构建议：

```
一句身份定位（我是谁，对口在哪）
一到两条最强匹配点（必须带具体项目名和数字）
一个具体问题（促回复，问句的回应率高于陈述句）
```

### 6.3 质量把控（四道）

1. **喂用户自己的反面词表**。`内容工厂/写作偏好/AI通病收集.md` 里那套「省 + 演」两大家族病例，直接编译成禁令塞进 prompt。**这是竞品抄不走的资产**，即投用的是通用大模型 + 通用 prompt，写出来就是标准 AI 腔。
2. **强制具体性**：必须引用 JD 里的原词，必须点名简历里的具体项目名和数字。禁止「丰富的经验」「深入理解」「高度契合」这类空词。
3. **生成后自检重写**：模型输出后，按 checklist 自评一遍并重写。便宜且效果明显。
4. **人工审核闸口**：审核页支持单条重生成、手改。改动全部记入 `greeting.history` 和 `annotation.greetingEdited`。

### 6.4 不做的

不做模板 A/B 打 tag。第一版没有回复数据，A/B 无法判定胜负，做了也是自欺欺人。**代价要明说：招呼语质量的唯一裁判是用户自己的眼睛。**

### 6.5 降级链

LLM 超时或失败时，逐级降级，**绝不阻断投递**：
`岗位定制招呼语 → 岗位组通用招呼语 → 用户自定义全局招呼语 → 出厂兜底语`

## 7. 去重设计

### 7.1 四层

| 层 | 判据 | 覆盖 | 时机 |
|---|---|---|---|
| L1 | `jobId` 精确匹配 | 同一岗位 | 召回后立即 |
| L2 | `fingerprint`（公司ID + 归一化岗位名 + 城市 + 薪资区间） | 下架重发换了 ID | 召回后立即 |
| L3 | 同公司内 JD 文本相似度超阈值 | 一坑多 HR、马甲岗 | 拉完 JD 后 |
| L4 | HR 冷却：同公司同 HR，14 天内不重复 | 防止轰炸同一个人 | 投递队列组装时 |
| L5 | 「继续沟通」按钮判别 | 手动聊过的、库里没有的 | 投递那一刻 |

### 7.2 岗位名归一化规则

去除装饰性内容后再算指纹，否则 L2 会大面积漏判：

```
去括号内容：（急招）（双休）（Base北京）(J10086)
去届别前缀：25届 / 26届 / 校招 / 社招
去紧急词：急聘 急招 高薪 诚聘
统一全半角、去空格、转小写
```

### 7.3 关于不做冷启动回读

用户已明确不做。后果是：**插件不知道装它之前手动聊过哪些岗位，会重复投**。

由 L5「继续沟通」判别兜底。这个方案零成本、准确，且不需要提前扫任何东西。代价是重复的岗位仍然占用一次详情页请求，但不会真的发出招呼语，也不消耗沟通额度。

## 8. 投递执行

### 8.1 额度与刹车

```
软上限   75/批（用户已定）
日上限   150（与即投一致，作为绝对红线）
硬探测   检测到「次数已达上限」/ captcha / code:37 → 立即停止，记录当日真实额度
```

连续跑一周后，`dailyQuota.actualLimit` 就是你账号的真实边界，软上限可据此调整。

### 8.2 节奏参数

与即投基本一致，不额外保守。真正的瓶颈不是间隔，是页面跳转耗时。

| 参数 | 即投 | 闪投 | 说明 |
|---|---|---|---|
| 岗位间隔 | 2 到 4 秒 | **2 到 4 秒随机** | 一致 |
| 批次休息 | 每 50 个休 90 秒 | **每 50 个休 90 秒** | 一致 |
| 并行度 | 3 worker（独立后台窗口） | **1，串行** | 75 个串行只要 15 到 20 分钟，不值得引入并行的复杂度和风控面 |
| 拉 JD 间隔 | 3 秒 | **3 秒** | 硬线，1.5s 触 `code:37` |
| 时段 | 无限制 | **避开 0 点到 7 点** | 凌晨批量操作特征明显，这条保留 |

**耗时估算**：单岗真实开销 = 详情页加载 + 点击跳转 + 发文本 + 上传两张图 ≈ 8 到 15 秒，加 2 到 4 秒间隔，约 12 到 18 秒。75 个串行加一次 90 秒休息，**总计 15 到 22 分钟**。

并行 worker 留作后续优化项，只在实测确认串行确实太慢时才做。

### 8.3 风控退避

12 小时滚动窗口内统计 captcha 次数：

```
0 次 → 正常速度
1 次 → 降速档（间隔 ×2），并弹窗告知用户
≥2 次 → 拒绝整批，冷却到窗口滑出，强制用户手动确认才能继续
```

检测到 captcha 立即暂停并把当前进度落盘，用户处理完验证码后可断点续投。

### 8.4 投递流程（逐岗串行）

```
1. 预检：关闭 BOSS 自动招呼语开关（updateGreetingV2 status=0）
2. 打开岗位详情页，停留 3 到 8 秒（模拟阅读）
3. 读 a.btn-startchat 文案
   ├─ 「继续沟通」→ 跳过，记 skipReason=already_chatted
   └─ 「立即沟通」→ 点击
4. 整页跳转到 /web/geek/chat
   └─ 若弹「沟通新职位」确认框 → 点确认
5. 发送招呼语文本
6. 上传并发送简历截图 ×2
7. 记录 conversationId、状态、时间戳落库
8. 随机等待 15 到 40 秒，下一个
9. 任务结束：恢复 BOSS 自动招呼语开关原状
```

### 8.5 分档凑满

```
先投 90+ 档，不够 →
放宽到 80+ 档，不够 →
放宽到 70+ 档，不够 →
放宽到 60+ 档（地板，绝不再降）
→ 仍不足 75 个，就投多少算多少
```

**地板分 60 是硬约束。** 没有它，岗位荒的日子系统会凑一堆无关岗位，「闪投」就退化成海投了。

UI 上如实显示构成：「今日 75 个岗位中：90+ 档 20 个、80 档 30 个、70 档 25 个」，并允许用户一键关掉凑数、只投高分。每条记录写 `dispatch.tier`，这是将来验证匹配模型是否有效的关键切片维度。

## 9. 公司库设计

### 9.1 两级维护

| 层 | 规模 | 内容 | 维护强度 |
|---|---|---|---|
| 精维护层 | 约 120 家 | 国内 Top 100 + AI 模型公司 + 音乐泛娱乐 | 手工核对别名和主体 |
| 词典层 | 约 380 家 | 创业公司、外企、长尾 | 只存名字，勾选时现场解析 |

### 9.2 分组

大厂主体（字节系 / 腾讯 / 阿里蚂蚁 / 百度 / 美团 / 京东 / 拼多多 / 快手 / 小红书 / 网易 / 滴滴 / B站）· 硬件与制造 · **AI 模型公司** · 游戏与内容 · **音乐与泛娱乐** · 金融科技与 SaaS · 出海 · 外企中国区

### 9.3 别名问题

**这是「只投大厂」最大的坑**。字节在 BOSS 上的主体可能是「字节跳动」「抖音」「巨量引擎」「北京字节跳动科技有限公司」等多个号，靠公司名模糊匹配一定漏。

做法：库里存「公司名 + 别名集合」，**首次勾选时自动去 BOSS 搜索解析出 brandId 并缓存**，之后用 ID 精确匹配。brandId 是平台内部 ID，无法预先写死在库里，必须运行时解析。对用户是无感的，第一次多花两秒。

### 9.4 用户扩展

- 搜索框输入公司名，实时查 BOSS 品牌库，确认后加入白名单
- 自定义分组保存（如「大厂 AI 产品岗」「音乐公司」），切换着跑

## 10. 界面

### A 页 · 配置

照即投那套面板做（它的信息架构是对的），**加两样它没有的**：

1. **公司模块**（放在「期望职位」下方）：内置分组勾选 + 搜索添加 + 自定义分组
2. **召回预估条**：每改一个条件，实时显示预计召回岗位数、够不够今天的 75 个额度、预计抓取耗时

保留即投的两个好设计：
- **HR 活跃度默认锁「3日内活跃」**。这是零成本的原生参数，对回复率的影响可能比我们的四维打分还大。
- **代价警示**。选到会大幅缩小池子的条件时当场提示，比如双休那条。

### B 页 · 审核

岗位卡列表，每张卡显示：总分 + 四维条形图 + 证据配对（可展开）+ concerns + 招呼语（可编辑/重生成）+ 勾选框。

顶部固定：已选 N / 75，分档构成实时显示。

### C 页 · 看板

今日进度、历史任务、分档构成、实际达成额度、captcha 记录。**漏斗区域先放占位**，等回复统计上线后填。

## 附：法律与风险

- 抓取与自动投递**违反 BOSS 直聘用户协议**，存在账号被限流或封禁的风险。半自动形态（用户审核后投递）风险显著低于无脑海投，但不为零。
- 平台的第一层惩罚是弹验证码而非封号，只要探到边界就停、不硬顶，风险相对可控。
- 第一版自用。若将来对外发布，需要在显著位置告知风险，并提供完全手动模式。
- 即投的源码仅用于核实平台客观参数（接口路径、风控阈值、字段结构），不复用其代码实现。
